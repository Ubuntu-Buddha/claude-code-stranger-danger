# How it works

The gates (the reader gate, the launch gate, the reader-tools hook, the settings guard and the terminal gate) are Claude Code `PreToolUse` command hooks (the [update reminder](#update-reminder) and the other session and prompt hooks never block a tool call), declared in [`hooks/hooks.json`](../hooks/hooks.json) and run as `python3 -I <script> || exit 2`. Each reads the hook input (JSON on stdin) and usually either:

- **denies:** prints one line to stderr and exits 2. Claude Code blocks the call and shows the line to the model, which then knows which reader to brief; or
- **stays silent:** exits 0 with no output. Your permission rules and the auto-mode classifier still decide.

The reader gate, the reader-tools hook and the settings guard never return "allow" (which would skip your rules) or "ask". The launch gate returns "ask" in one case (extra network hosts). The terminal gate is the exception by design: it answers "ask" for a check line you approve at the prompt, and "allow" only for reading or closing a tab it opened. Elsewhere a prompt approved in passing isn't a review.

## Configuration

One file: `~/.config/stranger-danger/config.json` (template in [`templates/config.json`](../templates/config.json)).

- **No project override.** Nothing in a project folder is read, so a repo can't loosen the gates. Home is the account's home folder, not `$HOME`: a project's settings `env` can set `HOME` for hooks, so a `$HOME` that resolves elsewhere fails closed too (VERIFY row 46). The reader gate, the log and the scan, canary and update-reminder hooks do this (the last three then do nothing); the launch gate finds its config file the same way, and the settings guard still uses `$HOME`. A user id with no account entry blocks every gated call.
- **Missing file:** the built-in rules apply. Web access is for the web reader only, private hosts are refused, and secret paths are closed.
- **Fails closed when the file is wrong.** The file is refused, and every gated call blocked until it's fixed, when:
  - it or its folder is writable by group or others, or owned by someone else;
  - it isn't a regular file, is over 1 MB, or isn't valid JSON;
  - it has a key nothing reads, at the top level or inside `reader_gate`, `launch_gate` or `coordinator` (such as `reader-gate`, `readerGate` or `untrusted-paths`), or the same key twice in one object, so a typo can't switch a rule off;
  - an `untrusted_paths` or `quarantine_paths` entry holds a wildcard, a root or `secret_paths` entry starts with `~` but isn't `~` or `~/...` (`~user` isn't expanded), a `secret_paths` entry has a `.` or `..` segment, or a `private_hosts` entry isn't a bare host name (a scheme, port, path, `*` or `@`), so an entry that could never match can't pass for a rule.
- **The `coordinator` section** is written by the setup's coordinator step, and read by the coordinator skill and the doctor, never by a gate. A bad value there makes the doctor fail; it doesn't block your tools.

| Key | Meaning |
|---|---|
| `reader_gate.untrusted_paths` | Folders only `document-reader` may read. Absolute or `~/`, no wildcard. |
| `reader_gate.quarantine_paths` | Folders only `quarantine-reviewer` may read or list. |
| `reader_gate.secret_paths` | Extra secret globs, added to the built-in list. |
| `reader_gate.private_hosts` | Extra host suffixes WebFetch never reaches. |
| `launch_gate.allow` | Exact command prefixes the launch gate lets through, as token lists, for example `["npx", "--no", "prettier"]`. Never applied across a pipe, and never relaxes the ssh or package-lane checks. |
| `launch_gate.ssh_hosts` | The only hosts `ssh` and `scp` may reach, jump hosts included, as you type them (a `~/.ssh/config` alias or a host name), for example `["myserver"]`. Unset: any host. |
| `launch_gate.ask_for_domains` | On (`true`) by default: a Bash or Monitor call that asks for extra network hosts (`allowed_domains`) goes to Claude Code's permission prompt. `false` refuses such calls instead. Set it to `false` if an allow rule, another plugin's hook, a PermissionRequest hook or an SDK callback could approve the prompt for you, or if you haven't run [VERIFY](VERIFY.md) row M2 yourself, in the permission mode you use; it checks what your version does. |
| `coordinator.project` | The coordinator's project folder, as a real absolute path. Not your home folder or `/`. See [COORDINATOR.md](COORDINATOR.md). |
| `coordinator.name` | Its display name, plain words of up to 60 characters. Cosmetic: recognition rests on the folder. |

## Who counts as a reader

A call is a reader's only when all of these hold:

1. `agent_type` is exactly `stranger-danger:web-researcher`, `stranger-danger:document-reader` or `stranger-danger:quarantine-reviewer`. The prefix is read from the plugin's `plugin.json`. Bare names like `web-researcher` never pass, because any project can define an agent with that name and give it a shell.
2. `agent_id` is present and well formed, so the call really comes from a subagent.
3. No file under a `.claude/agents` folder contains `stranger-danger:`. The folders checked are `~/.claude/agents` (and `$CLAUDE_CONFIG_DIR/agents`), `$CLAUDE_PROJECT_DIR/.claude/agents`, and the `.claude/agents` folder in the working directory, the project folder and each folder above them, up to home (or `/` outside home).
   - Every file counts, not only frontmatter: any name, extension or letter case, up to 8 folders deep, through symlinked files and folders. A BOM is stripped and the bytes decoded leniently, and the text is also searched with hidden characters removed, case folded and YAML escapes resolved. A file or folder named `stranger-danger`, or whose name contains `stranger-danger:`, counts too.
   - The check fails closed: folders more than 8 deep, more than 2,000 files, a file over 1 MB or more than 32 MB in all also turn the readers off, as does a working or project folder the hook is given that isn't an absolute path or is nested more than 64 folders deep.
   - So name the readers in `CLAUDE.md` or your rules file, not in your own agent files.
4. The plugin's own definition of that reader still has a narrow `tools:` list:
   - the web reader: ToolSearch, WebSearch and WebFetch;
   - the other two: Read, Grep and Glob;
   - and no MCP servers.

If a call claims to be a reader and fails one of these, it's treated as an ordinary agent, and the deny message says which check failed.

## Reader gate decisions

**WebSearch, WebFetch.** Only the web reader. For WebFetch, the URL is checked for everyone first. It is refused when:
- the scheme isn't http or https, or the URL has user info, a backslash, a percent-encoded host, or control or invisible characters;
- the host is an IP literal in any spelling (`127.1`, `0x7f.1`, `2130706433`, `[::ffff:127.0.0.1]`), a single-label name, or ends in `localhost`, `local`, `internal`, `home.arpa`, `lan`, `home`, `corp` or a `private_hosts` suffix;
- (for the web reader) the name resolves to an address that isn't globally routable: loopback, private, link-local, CGNAT, multicast, reserved, documentation ranges, or cloud metadata. Mapped, 6to4 and NAT64 forms are unwrapped first. A lookup that fails or takes over 2 s is logged, and the fetch is let through to fail on its own.

**Read.** The path is expanded the way a shell does, then checked in three forms: the normalized path, its `realpath`, and the `realpath` of the normalized path. That covers symlinks and `..` tricks, including the case where a tool normalizes `a/link/../b` before opening it. The checks run in this order:
1. **Path tricks:** control or invisible characters (Unicode Default_Ignorable code points and format characters), components with leading or trailing blanks, `/proc/<pid>/{cwd,root,exe,fd,map_files,ns,…}`, `/proc/self` and `/dev/fd` are refused, ignoring case on macOS. The gate also follows the path's symlinks itself, link by link (up to 40), in both the path as written and its normalized form, and refuses one that passes through any of these on the way, even when `realpath` resolves it (a link to `/proc/self/root` resolves to `/`), or whose links can't be followed. Under `/proc/<pid>/` (and `task/<tid>/`) only `status`, `stat`, `statm` and `limits` are readable; `/proc/<pid>` itself, `/proc/cmdline`, `/proc/keys` and `/proc/kcore` are refused. Everything under `/dev` is refused except `/dev/null`, `/dev/zero`, `/dev/full`, `/dev/random` and `/dev/urandom`; elsewhere, block and character devices (unless their device number is one of those five), FIFOs, sockets and paths whose type can't be checked are refused.
2. **Secrets:** a match against the built-in or configured secret patterns is refused for everyone, readers included. `.env.example`, `.env.sample` and `.env.template` are allowed. A `.npmrc` or `.yarnrc.yml` anywhere is a secret too (registry logins), except that the quarantine reviewer may read one with Read, or Grep with the file itself as its path, inside a quarantine folder (judged at its real path too; a Grep glob naming one and `~/.npmrc` stay refused). A quarantine folder at or above your home folder gets no exception; keep a quarantine folder to strangers' files only, since one that also holds your own projects opens their registry configs to the reviewer. Patterns that start with `**/` match anywhere, inside any project too. A pattern's literal folder (`~/.ssh` in `~/.ssh/**`) is also matched at its resolved forms, so a secret folder that is a symlink, or sits under one, is refused at its real path as well. Claude Code's `~/.claude.json` and its backups (`~/.claude.json.*`, `~/.claude/backups/`), `~/.claude/.credentials.json`, its IDE lock files (`ide/`, which hold an auth token) and saved session environments (`session-env/`) are secrets; under `CLAUDE_CONFIG_DIR` the same files in that profile are too. Desktop apps' session stores (Claude Desktop, Slack, Discord: `Cookies`, `Local Storage`, `IndexedDB`, `Partitions`, `Network` and the like, plus Claude Desktop's `claude_desktop_config.json`) are secrets by name; the rest of each app folder stays readable.
3. **Transcripts:** Claude Code writes every agent's tool results under `~/.claude/projects` (and under `$CLAUDE_CONFIG_DIR/projects`): session transcripts, subagent transcripts and large results saved as files. `$XDG_CONFIG_HOME/claude` and `~/.config/claude` are treated the same when they exist. A background task's `tasks` folder, and the files in it, under the per-user temp folders (`$TMPDIR/claude-<uid>`, `/tmp/claude-<uid>`, `/tmp/user/<uid>/claude-<uid>`) is refused for everyone, the agent's own included (VERIFY row 47); the rest of those folders, the scratchpad, stays readable. A Grep rooted at the temp folder or above it is refused whatever the glob. A Grep or Glob rooted at a project or session folder is refused while a `tasks` folder exists below it (a Glob when its pattern could list the task files); a Grep at a project folder is refused whatever the glob when a session's `tasks` folder lies below it; for a session folder, or a project folder with `tasks` directly in it, a Grep glob anchored to a sub-folder other than `tasks` passes. A web reader's fetched pages land there too. Everything there is refused for everyone except a project's `memory` folder, plus one exception: an agent may Read its own saved tool output. That's a file directly in its session's `tool-results` folder that its own transcript records saving, in the form Claude Code 2.1.280 writes. A path quoted in some tool's text or a file listing doesn't count, and anything unexpected (a missing, linked or oversized transcript, more than 1,000 matches) counts as no record.
   Claude Code's other records, in `~/.claude` and under `$CLAUDE_CONFIG_DIR`, are refused for everyone with no exception: the prompt history (`history.jsonl`), the copies it keeps of edited files (`file-history/`), its debug logs (`debug/`), pasted and uploaded text (`paste-cache/`, `uploads/`), shell snapshots (`shell-snapshots/`) and to-do lists (`todos/`). The settings template denies these to sandboxed commands too, except `shell-snapshots/` and `session-env/`, which sandboxed Bash needs to read.
4. **Quarantine** folders: the quarantine reviewer only.
5. **Untrusted** folders: the document reader only.
6. **Confinement:** the web reader reads nothing; the document reader reads only inside untrusted folders; the quarantine reviewer only inside quarantine.

**Grep.** The same checks run on the search root, without the saved-output exception, plus:
- a Grep rooted at `/`, `/proc`, `/dev` or your home folder is refused;
- a glob aimed at secret file names (`.env*`, `*.pem`) is refused unless it also matches ordinary names. A glob with a folder in it is also tested whole against secrets known by folder and name (`.aws/credentials`, `**/.kube/config`, `.ssh/*`), with each inner `**/` also read as no folder (`.aws/**/credentials`), unless it also matches an ordinary path; a glob with no folder is also tested against those files' names (`credentials`, `auth.json`), since it matches at any depth. The README lists the globs this refuses that could have matched only ordinary files. Brace alternatives (`{.env,.env.local}`, nested too) are expanded first and each one judged on its own, and backslash escapes (`\.env`) are read the way ripgrep reads them. A glob with an unclosed `{`, braces nested more than 8 deep or more than 256 alternatives is refused;
- a Grep rooted at a folder that a folder-and-name pattern names (`.aws`, `.docker`, `.kube`, `.aptos`, `keystore`, `containers`, by its real name too) is refused unless its glob is anchored to a sub-folder;
- a Grep whose root contains a folder the caller may not read (in any of its spellings, so the real parent of a symlinked folder counts) is refused unless its glob is anchored to a sub-folder that avoids it (a glob starting with `!` or `#` anchors nothing). Globs are anchored to the search folder, not the working folder (checked on 2.1.296);
- a glob with a space is refused, because Claude Code splits a glob on spaces and on commas (unless it holds braces). Each comma-separated piece is judged on its own, for the secret-name check too. A glob with braces is kept whole (checked on 2.1.296), and its comma-split reading is judged too when every piece is a glob. A glob with braces and a comma outside them, which could be read either way, is refused, and so is a piece with an unclosed `[`.

**Glob.** Listing names inside quarantine is for the quarantine reviewer only, including through a pattern that walks into it. The gate reads a pattern the way Claude Code's Glob does (checked on 2.1.296): a relative pattern with no `/`, and what follows an absolute pattern's literal folders when it has no `/`, match file names at any depth, so `*.md` from your home folder walks into quarantine. Brace alternatives (`{a,b}`) are expanded and each judged on its own; one that climbs with `..`, or starts with `/` or `~` inside a relative pattern, is refused, as is a pattern whose braces can't be expanded. Any segment with a wildcard (`*`, `?`), a backslash escape (`\q`, which ripgrep reads as `q`) or an extglob opener (`@(`, `+(`, `!(`) counts as matching any name, and one with a character class (`[…]`) as matching any number of folders, because a class like `[!x]` matches `/`. A part starting with `!` or `#` (so an extglob `!(` too) is refused, since ripgrep reads it as a negation or a comment and lists everything; so are a part that starts or ends with blank space, a part with `**` inside it (`a**b` counts as crossing folders), a folder argument with a wildcard other than `[` and `]` (the tool takes the folder literally; when the folder holds a bracket, folder and pattern are also judged joined as one absolute pattern, in case a version reads them that way), and a pattern over 4,096 characters. A pattern that names one path exactly is also judged at that path, in case it's a symlink. No Glob may list names in `/proc` or `/dev`, or walk into them. Readers stay confined the same way as for Read. Then, with Grep's exemptions, no Glob may list names inside a secret folder (one whose entries a pattern covers, such as `~/.ssh/**` or `~/vault/*`), Claude Code's transcripts and other records, or, for anyone but the document reader, an untrusted folder: not from that folder, and not by walking into one (the refusal suggests an anchored pattern such as `src/**/*.py`). A folder secret by name anywhere (`**/.ssh/**`) is refused when the Glob starts inside it or a pattern segment names it. A project's `memory` folder stays listable, and a quarantine folder inside an untrusted one is left to the quarantine rule. An untrusted folder inside quarantine stays closed to the quarantine reviewer, and the quarantine rule keeps the document reader out of it. The *names* of secret files in an ordinary folder (`**/.env`) can still be listed; only their contents are refused.

**Grep limits (documented, not fixed).** Two Grep cases can still print lines from a secret file. A glob that also matches ordinary names (`*`, `*.json`) isn't counted as aimed at secrets, so it reaches any secret file it also matches. A Grep over a folder with no glob searches every file ripgrep doesn't skip, a non-ignored `.env` inside it included. The README's limits list says what covers them.

## Launch gate decisions

The launch gate is a tripwire, not a security boundary. It catches the usual ways an agent reaches for a launcher, a piped download or `sudo`. It can't see what a script, Makefile or `package.json` script runs. Except the known gaps below, what a runner runs (`uv`, `poetry` or `pdm run`, node's npm script, corepack, npx's and `npm exec`'s `-c`, `pnpm exec`, `yarn exec`, `bun exec`, `npm explore`) gets the same checks as a command typed at the top level, and the allow list relaxes a runner by its own name only. Where reading a form exactly would mean modelling more of bash, the gate refuses it (`launch-hidden-command` or `launch-unparseable`) with a line that says what to write instead: arithmetic (`$(( ))`, `(( ))`, `$[ ]`) holding a `#` at its start or after a blank, a carriage return, `;`, `&`, `|`, `(`, `)`, `<` or `>` (where one of the gate's readers would take it as a comment), a line break or (in `$[ ]`) a quote; a list or pipeline substitution in command position or under `eval` that holds anything but `printf`, `echo`, `true`, `:`, `head` and `tail`, or joins commands with `&&`, `||` or `&` rather than `;` or a line break; a download piped into a runner whose shell text (`-c`/`--call`, `npm explore`, `pnpm exec`, `yarn exec`, `bun exec`) the gate can't split or holds a `$` or substitution in a command word (one whose text runs a shell or another interpreter that reads stdin is refused as a piped download); a `[[ ]]` the parser can't step through; an option it doesn't know before uv's, Poetry's or PDM's subcommand; a word that mixes an expansion with written `IFS` text where the word as written isn't known; `mapfile -C` or `readarray -C` with a callback built at run time; a `PS0`, `PS1`, `PS2`, `PS4` or `PROMPT_COMMAND` value that holds a substitution; and `${x@P}` on a value it doesn't know. A few unusual but harmless commands are refused that way too. Beyond what the [claims](CLAIMS.md) list, it does not follow names, options or word splits built at run time (arithmetic, `eval`, payloads, traps, `IFS` and the like). The control for downloads is the sandbox with `sandbox.network.allowedDomains`; the README's [limits](../README.md#what-this-does-not-do) say more.

Known limits and gaps (no fix in v0.2.0; the gate is a tripwire, not a security boundary, and a redesign is planned for v0.2.1). The v0.2.0 review found forms the gate does not read, in three kinds. Each can let a command past a check, so don't rely on the gate where that matters. They override every statement in this section about what is denied, refused or checked. The exact forms aren't listed here, so this page doesn't work as a list of ways around the gate:

- **Hidden operators:** some shell syntax can hide a command from the gate or make it skip what follows.
- **Piped launchers:** some ways of running a downloaded script through an interpreter, a shell or a runner's shell text are not seen as a download piped to a shell.
- **Unknown options:** options, aliases and subcommands of package managers and runners that the gate's tables don't hold can make it read a command wrongly, or not see through it.

The command is split into simple commands across `;`, `&&`, `||`, `|`, `&`, newlines, `$(…)`, backticks and process substitution. Quoting is undone (`n"p"x` is `npx`). Wrappers are stripped: `env`, `command`, `exec`, `nohup`, `time`, `nice`, `timeout`, `xargs`, `stdbuf` and leading `VAR=value`. Payloads of `bash -c`, `sh -c` and `eval` are checked recursively, up to depth 4. Every check also reads through runners: the command after `uv`, `poetry` or `pdm run` (`run` counts only as the subcommand, after the global options and their values), node's npm or npx script, `npx-cli.js` run directly, the tool after `corepack`, the command or shell text after npx, `npm exec` (also `-c`/`--call`), `npm explore <pkg> --`, `pnpm exec`, `yarn exec` and `bun exec`; that command is checked as one typed at the top level. npm's, pnpm's, Yarn's and Bun's subcommand is found with one table of their options before it (those that take a value and common ones that take none); an option in neither, with no `=`, is read both ways. `$((` is read as arithmetic only when bash would (the `)` that closes its second `(` is followed at once by another `)`); otherwise it is a command substitution and is checked as one. A word is split as bash splits it (at `IFS`, a carriage return being part of a word); where a finer split would read other words, the call is read that way too.

It denies (except the known gaps above):
- **launchers:** `npx` without `--no`, `npm exec`/`x`, `npm create`, `npm init <pkg>`, `pnpm dlx`/`create`, `yarn dlx`/`create`, `bunx`, `bun x`/`create`, `uvx`, `uv tool run`/`install`, `uv run --with`, `pipx run`/`install`, `cargo install`/`binstall`, `go install`/`run` with `@version`, `gh extension install`, and `deno run`/`install`/`x` with a remote specifier;
- **downloads run directly:** a download (`curl`, `wget`, `fetch`, `iwr`, `irm`, `nc`) piped or substituted into a shell or an interpreter that reads its program from stdin, and a download saved and then run in the same command;
- **privilege:** `sudo`, `su`, `doas`, `pkexec`, `run0`;
- **agents with guardrails off:** `claude --dangerously-skip-permissions` or `--permission-mode bypassPermissions`, `codex --dangerously-bypass-approvals-and-sandbox` or `--yolo`, and `gemini --yolo`;
- **ssh, scp and sftp beyond plain remote access.** If your sandbox config lists them in `excludedCommands` so agents can reach your servers with your keys, they run **outside** the sandbox, and so does anything they launch. The gate denies:
  - options that run a local command or load a library: `-o ProxyCommand`, `LocalCommand`/`PermitLocalCommand`, `KnownHostsCommand`, `Match`, `Include`, `PKCS11Provider`, `SecurityKeyProvider`, `XAuthLocation`, `-I`, `-F <file>` (`-F none` is fine), and `scp -S`/`-D`, in any spelling (`-oProxyCommand=…`, `-o 'ProxyCommand …'`, any letter case, bundled flags, options after the host);
  - port forwarding and tunnels: `-L`, `-R`, `-D`, `-W`, `-w`, `-O` and their `-o` forms;
  - shared connections, which leave an ssh process running outside the sandbox after the call: `-M`, `-S`, `-o ControlMaster`, `ControlPersist` and `ControlPath`;
  - `-E <log>` and known-hosts files other than `/dev/null` (they write outside the sandbox), `-o HostName` (it changes the host), and `SendEnv` (it ships local environment variables);
  - `sftp` entirely: its batch input runs `!command` locally. Use `scp`;
  - at the top level, anything alongside them: a pipe, `;`/`&&`, `$(…)` or backticks (in a heredoc too), a wrapper such as `timeout` or `env`, a `VAR=value` prefix such as `LD_PRELOAD`, or a file redirect other than `/dev/null`. Filters go inside the remote command: `ssh host 'journalctl -u app | tail'`;
  - with `launch_gate.ssh_hosts` set, any destination, `-J`/`ProxyJump` hop or `scp` remote that isn't listed;
  - text that names `ssh`, `scp` or `sftp` anywhere (also with quotes, backslashes or `$''` inside the name, or a `$'…'` escape that can spell a letter) and has a second line, a carriage return, `<<`, `$((` or `$[`, or doesn't parse. The gate's parser can be misled there into missing a second command beside ssh, so it doesn't trust the parse. A heredoc to a remote shell, a here-string and a multi-line commit message that mentions ssh are refused too;
  - a word in an ssh-family command that bash would expand before ssh sees it: an unquoted `$`, `{`, `}`, `*`, `?` or `[`, or a `$` inside double quotes. The gate checks words as written, so an expansion could build an option it never saw. Put anything for the remote side in single quotes (`ssh host 'echo $HOME'`).

  Still allowed, and still worth reading in the prompt: `scp` can copy any local file it can read to a listed host, and `-A` forwards your agent. Keep ssh on `ask`.

A redirect that names its file descriptor (a number, or bash's form that stores it in a variable) is read as a redirect, not as the command. Words are brace-expanded as bash does (not leading assignments, which bash leaves alone) before any check, so a command, subcommand or payload built from braces is checked as bash will run it; one that makes more than 1024 words from a word, 4096 in a call, sits in a word over 1024 characters, or shares a word with an empty `{}` is refused. Bash drops a word that comes out empty (an unset variable, `$@`, an empty substitution, a glob under `nullglob`), so when words up to the command word are built at run time, the gate also checks the command as bash would run it with them empty: every combination for up to 6 such words, each alone and all together for 7 to 16, and more than 16 are refused. The command word is found again after each drop, so a wrapper's operands count, and a command word that still holds a `$` after the wrappers are stripped has its next word checked too. The pipe checks (a download or decoder piped into a shell, a download run in the same call) run once more with all such words empty. Some mixes it doesn't try can still get through.

**Per-call network hosts.** A Bash or Monitor call with a non-empty `allowed_domains` would reach hosts past your sandbox's network allowlist for that command. Once every other check has passed, the gate hands it to Claude Code's permission prompt (a hook "ask"), with a reason that starts with a fixed warning and then names each host. On Claude Code 2.1.309 ([VERIFY](VERIFY.md) row M2), in the rounds whose prompt wording was recorded, that reason wasn't shown: the prompt was Claude Code's own, showing the command and each host. The ask is a request for a prompt, not a block. Claude Code's docs say a hook's ask still prompts in auto mode, and that a headless run denies it unless something approves it. On 2.1.309, for Bash, in auto mode with the sandbox on, the gate asked and a prompt appeared each time, even with allow rules `Bash(true)`, `Bash(true *)` and `Bash(*)` (row M2); whether Claude Code would prompt for the hosts without the gate wasn't tested. Whether an allow rule skips it in other permission modes, on other versions or for Monitor, and whether another plugin's hook, a PermissionRequest hook or an SDK callback can approve it unseen, isn't documented or tested. If you use any of those, or haven't run M2 yourself in the permission mode you use, set `launch_gate.ask_for_domains` to `false`, and such calls are refused as before. The doctor warns when the setting is on and a Bash or Monitor allow rule with a wildcard is present in your user, project or managed settings; an exact rule isn't flagged, and isn't known to be safe either. The call is refused instead from a subagent (a subagent's own permission mode may not be the one the event reports), in the `dontAsk` and `bypassPermissions` modes, and when the event doesn't say its mode. Only names that fit a strict grammar are shown: a host name of two or more labels whose last label is letters only (or punycode), or a public IPv4 address (not multicast), either with an optional port, at most 10 of them and 300 characters in all. Wildcards, local names (`localhost`, `.local`, `.internal`, `.home.arpa`, single labels) and private, loopback or link-local addresses are refused. So only characters a host name can hold reach the prompt, though a host name can still be made of words. The gate never adds a host to `sandbox.network.allowedDomains`; to trust one for good, add it yourself.

**Monitor** (v0.1.1). `hooks.json` runs the gate for `Bash|Monitor`. A Monitor command gets every check above, ssh included. A Monitor input field outside `command`, `description`, `timeout_ms`, `allowed_domains` and `ws` is refused, with the field's name, since a new field could change what runs or where. A WebSocket watch (`ws`) is refused, and so is a Monitor command whose text names a downloader or raw network client (`curl`, `wget`, `fetch`, `nc`, `socat` and the like) or bash's `/dev/tcp` paths anywhere, or builds its command name from a variable, a glob or a substitution, or holds a `$'…'` string with a letter-building escape anywhere. It reads the words after brace expansion and follows shell `-c` payloads and `eval`. It's a tripwire, not a boundary: a name built some other way can still get through. The reason: a watch streams outside text into the agent for as long as it runs, and only the web reader reads the web. Other watches can still carry outside text (`tail -f` of a file a stranger wrote, a remote log over `ssh`); the rules file covers those. [VERIFY](VERIFY.md) row M1 showed Claude Code runs the hook for a main-session Monitor call on 2.1.301, and again on 2.1.309 (a subagent's wasn't tested); the hook docs don't list Monitor as a matcher, so the settings template still denies Monitor until M1 passes on your version.

A command it can't parse falls back to a conservative text scan, unless it names the ssh family (above). Commands over 100,000 characters, or nested deeper than 4, are denied.

## Update reminder

`hooks/doctor_nudge.py` runs when a session starts or resumes (`hooks.json`'s matcher is `startup|resume`; `/clear` and compaction keep the process that was already running). It hashes the real path, size, inode, device and modification and change times of the first `claude` on an absolute `PATH` entry, plus the plugin's version, and looks for the hash among the last 8 in `~/.local/state/stranger-danger/last-seen.json`. When it's new, it saves it and prints fixed text: a `systemMessage`, shown to you, asking you to run `/stranger-danger:doctor`. It adds nothing to the session for Claude, since a note telling an agent to suggest something reads like the instructions the rules teach it to refuse. It uses nothing from the event (it reads its input only after printing, and drops it), runs no command, makes no network call and never blocks: an error before it prints means no reminder, it saves only after printing (so a state folder it can't write means a reminder at every start), it stops itself after 3 seconds, and it exits 0. Claude Code's docs say no exit code from a SessionStart hook blocks the session. No hook input or environment variable gives the Claude Code version (checked against the hooks and environment-variable docs, 2026-10-23, not every page in full), so a `claude` that isn't on `PATH`, such as the desktop app's own copy, isn't seen. In the desktop app the reminder may not show at all (in one check, the desktop app didn't show a session-start hook's `systemMessage`; README, the OSV check's limits), so there you run the doctor yourself after an update; a known limit, kept for after v0.2.0.

## Setup in chat and the settings guard

`/stranger-danger:setup` runs `skills/setup/chat.py`, which never writes your files. `check` reads your settings file and prints only the dotted names of values that look like secrets: an `env` entry whose name holds KEY, TOKEN, SECRET, PASS, CREDENTIAL, AUTH, COOKIE, SESSION, PRIVATE or BEARER, an `env` value with a run of 32 or more key characters, or a known key shape anywhere (GitHub, Anthropic and OpenAI-style, AWS, Slack, Google, GitLab, npm, PyPI, PEM blocks, Stripe-style, JWTs, a `Bearer` header, a `token=`, `api_key:`, `password=` or `secret=` assignment, a URL with a password in it). A key named twice in one object stops it too, since Claude and the plan might read different values. It also refuses while your deny list still holds v0.1's deny rules for these files, since a deny wins over the prompt. `plan` and `show` refuse until `check` passes. `plan` lists the changes `apply.py` would make, with the rules file's canary placeholder kept, no start-up paths taken from PATH, the session's working folder as the work folder, and the gate config left out. `show N` stages file N's exact new text in a private folder under `$TMPDIR`; Claude reads it and writes it with the Write tool, one prompt per file.

`hooks/settings_guard.py` runs before every Edit, Write, MultiEdit and NotebookEdit call. For a path in its zone (`settings.json` and `CLAUDE.md` in the profile folder and in `~/.claude`, anything in their `stranger-danger` folders, and anything in `~/.config/stranger-danger`), it lets through only a Write, and only when its text matches a change in setup's plan for that path, worked out from your files as they are, with and without the auto-mode rules. Edit, MultiEdit and NotebookEdit calls there are refused, since the guard can't be sure it would apply one exactly as the tool does. A path counts as in the zone as written, as its real path or with a leading `~/` read as your home, compared ignoring case (macOS disks ignore case by default); the file it names counts by device and inode, so a hard link elsewhere is caught, and so does each folder above it, so a guarded folder reached by another name is caught too. JSON is compared as JSON values of the same types (Python's `==` says `true` equals `1`), refusing duplicate keys, NaN and Infinity; other text is compared with trailing newlines ignored. A link, a `~user` path, a relative path with no working folder, a guarded name under a relative `CLAUDE_CONFIG_DIR`, or anything it can't work out is refused, with a message that says which. A call it lets through gets the normal prompt (from Claude Code's docs; whether every permission mode shows it, and whether hooks run before deny rules, are VERIFY.md row S1), because the template asks, rather than denies, for the settings file, that `CLAUDE.md` and the rules folder; the gate config stays denied, and the guard covers it too. It's a gate like the others: exit 2 refuses, any error or a 5-second alarm refuses, and refusals are logged with the code `settings-guard`.

## Approve-to-run

`hooks/terminal_gate.py` runs before the desktop app's Terminal-panel tools (`hooks.json`'s matcher is `mcp__terminal__.*`, the prefix those tools carry in the desktop app's tool list; whether the hook matches them live is VERIFY row T1; it handles run, read and stop and refuses the rest, and another server's tool that only has "terminal" in its name isn't affected) and after `run_in_terminal`. The panel's shell runs outside the sandbox, so a line sent there is yours to approve, and the gate holds what an agent may send to a short lane:

- a file check: `sha256sum` or `stat -c '%F %U %G %a %s %n'` of a path, optionally behind `sudo -k`;
- a unit check: `systemctl [--user] --no-pager is-active|is-enabled <unit>`;
- the password check, `sudo -k true`.

A path is absolute and plain (no `..`, `.` or empty part), under `/usr/local/bin`, `/usr/local/lib`, `/etc/systemd/system`, `/etc/systemd/user` or `~/.claude/hooks`, or `~/.claude/settings.json` (always that file, whatever profile folder `CLAUDE_CONFIG_DIR` names; the gate reads the profile's settings for its own checks). A `sudo` line may not name a file in your home folder. It is checked as written, with its folder resolved and a final link followed, and refused if it names a secret (`.env`, keys, tokens, `.npmrc` and the like), matches a sandbox `denyRead` entry or a `Read` deny rule in any settings file the gate reads, is a `sha256sum` target that isn't a regular file, or is a regular file with more than one hard link. The home folder is the account's, not `$HOME`'s.

A line that passes is answered `ask`: your approval at the permission prompt, which shows the whole line (a `sudo` line says a password prompt follows, and you type it only in the panel), is the OK for that one line. The call also needs the desktop app (`CLAUDE_CODE_ENTRYPOINT`), the main session (a subagent's call is refused), no `tab_id` or `cwd`, a permission mode where a hook's ask reaches you (`default`, `acceptEdits`, `auto`), and a settings state that leaves the prompt alone: no allow rule that could cover a terminal tool, no plugin other than this one enabled (and only one enabled key of this plugin across all the files), no permission-request hook, no hook of your own on terminal tools, rules not limited to managed ones, no server-managed cache, and `mcp__terminal__run_in_terminal` in the user settings' ask list (the settings template adds it). It needs an absolute working folder, to find project settings. The gate reads the user, project, local and managed settings files and the server-managed cache; it does not read settings from a `--settings` flag, environment variables or a plugin's own settings, so a rule there is not seen. The check and the run are separate steps, so a file can change between your approval and the command; the prompt shows the line, not the file's content.

`read_terminal` is allowed by the gate on a tab this session opened through an approved line, once, within five minutes, and never on a `sudo` line's tab (a password typed there by mistake would show). `stop_terminal_tab` is allowed on such a tab with `close: true`. Which tab a line opened is read from the tool's result by the after-hook; if it can't be read, no tab is owned. Every other terminal tool is refused (the settings template also puts `read_terminal` and `stop_terminal_tab` in the ask list and denies opening and listing tabs, so a refusal there doesn't depend on the gate alone). A tab id the app reuses is not owned. Whether a hook's allow also skips the template's ask rule for read and close is not checked ([VERIFY](VERIFY.md) row T1). The state is in `~/.local/state/stranger-danger/terminal-gate/` (mode 0700), refusals are logged with the code `terminal-gate` and no line text, and any error, bad input or a hang (a 6-second alarm and an 8-second backstop, under the hook's 15) blocks.

What it does not cover: a tab you open yourself, and anything you type in the panel; another plugin's hooks, which is why it refuses beside one; a managed `allowManagedHooksOnly`, which switches this plugin's hooks off (then the prompt, which shows the whole line, is the only check); and an unreadable result, which leaves a tab for you to read. It can't tell a tab you opened from one the gate counted: a tab you close yourself and an agent then names by the same id is the gate's known limit. It is a tripwire for what an agent sends, as the launch gate is. Install commands, unit actions and status checks aren't in this lane in this version.

## Instruction-file check

A sandboxed Bash command can create `CLAUDE.md`, `AGENTS.md`, `CLAUDE.local.md` and files under `.claude/` rules, agents, commands, output-styles and skills in the session's folder without a prompt, and Claude Code loads them as instructions (the maintainers' probe on one version, from its memory documentation [VERIFY]). `hooks/instr_check.py` runs at session start, resume, clear, after compaction and in a forked session (the last two from Claude Code's docs, not tested here [VERIFY]). For each fixed name in each folder from the session's folder up to the git repo root, it computes the file's git blob id itself and asks git only for `ls-tree HEAD` of that path; a file that is new, differs, is a link or can't be read is counted. Folders above the repo root, and any folder when there is no repo, are only counted ("not compared").

Git comes from a fixed list of absolute places (`/usr/bin/git`, `/usr/local/bin/git`, `/opt/homebrew/bin/git`, `/bin/git`), the first an executable file that neither group nor others can write; `PATH` is never read. It runs with a clean environment, no hooks, no fsmonitor, no shell, in its own process group that is killed on a timeout, and only after the repo's git config files pass an allowlist of sections and keys (an include, alias, filter, program setting, unknown key, alternates file or graft file means git isn't run and the files are only counted). The walk is bounded in depth, files, entries and time, and a cut is reported, never silent. The output is fixed text: names from the fixed list, a place word and counts, never a name from the repo or any file text, and the same lines go to the model, since the desktop app may not show `systemMessage`. If the check can't finish, one fixed line says so (except when the runtime kills it at its own time limit, which prints nothing [VERIFY]; a script killed by a signal after printing gets the fallback line after its output, which may read as two objects [VERIFY]); if the hook can't start (no `python3`), the hook command's fallback prints one fixed line. It always exits 0 and never blocks.

What it can't see is in the README under "What this does not do". A sandboxed shell can write most of `.git`, so `HEAD` isn't a trusted baseline: it is a signal that sends you to your own terminal, not a gate.

## Canary fill

The rules canary shows that a session loaded the rules, so no session may learn the word any other way. If an agent wrote it into the rules file, that session would know it without loading anything. So setup leaves the `Rules canary: <your-canary-word>` line as it is, and `hooks/canary_fill.py`, at the next session start or resume, fills in a random word (a word, a digit and a letter). It changes only a line that is exactly the placeholder line once stripped, never a word you chose, in `$CLAUDE_CONFIG_DIR/stranger-danger/RULES.md` (an absolute `CLAUDE_CONFIG_DIR` only) or `~/.claude/stranger-danger/RULES.md`. It leaves the file alone unless it's a regular file you own with one name (no hard link), not a link, in a folder that isn't a link, at most 1 MB of UTF-8 text. It writes a new file in the same folder with the old one's permissions, checks that the old one hasn't changed since it was read, and renames the new one over it. It shows you one of two fixed lines (filled, or left alone), never the word, and adds nothing to the session for Claude. Like the update reminder, it uses nothing from the event, runs nothing, makes no network call, stops itself after 3 seconds and exits 0, and like it, its line may not show in the desktop app (a known limit, kept for after v0.2.0).

The doctor's canary step then has the session state the word from its loaded rules and runs `doctor.py --canary 'WORD'`, which compares SHA-256 hashes of that word and the file's in constant time and prints only "matches", "doesn't match" or "not set". It takes only letters, digits, `-` and `_`, so the word can go in single quotes. While it runs, the word sits in its process arguments, where anything running as you can see it; the canary shows the rules loaded and was never a secret. The one-command install still fills in a word and prints it in your terminal, which no session sees.

## OSV check

`/stranger-danger:osv` (optional; setup's OSV option turns it on) runs `/usr/bin/python3 -I skills/osv/osv.py run` as one sandboxed Bash call, in the background. The runner:

1. picks the folders to scan: the ones you named, or the session's folder, each a real folder and not a link, at most 20. It refuses `/`, your home folder and folders above it, and system folders. The scan reads each 6 levels deep and skips `node_modules`, `.git`, `target` and the like, so a folder of several projects works. Below that it walks on by name only, to 32 folders below the folder named (or below a worktree's own top); past 100,000 folders below the read depth (counted separately for the folder and for each worktree) it stops listing deeper folders, and the 240-second listing limit bounds the whole walk. It counts the lockfiles, runtime pins, Dockerfiles and virtualenvs it finds there but doesn't read (`lockfiles_beyond_depth`, `runtime_pins_beyond_depth`; a file at the same path inside a worktree counts once, so the count is a lower bound). The summary and the doctor show their sum as a count, not as names, and say when that walk stopped early (`repo_walk_cap_hit`). Each folder under the named folder's own `.claude/worktrees` (normally git worktrees; nothing checks) is scanned the same way from its own top, up to 256; a link there isn't followed. Packages found in a worktree count as held, so a stale worktree shows its old versions until it's removed, and their names are sent like the repo's own. Worktrees of projects inside the named folder are walked as ordinary subfolders, so their deeper files count as below the read depth. A test pins the runner's 6 to the core's own limit and runs the core's walk on a tree 7 folders deep;
2. checks its tools: `bash`, `curl`, `jq` (1.6 or later) and `python3` in `/usr/bin` or `/bin`, each a file you don't own and can't write, in a folder the same (inside the sandbox on Linux, root's files show as owned by `nobody`, so it doesn't ask for root as owner). A missing or unfit tool stops it before any request;
3. checks `~/.cache/stranger-danger/osv/` (made where it can be, no link on the way, yours, set to mode 700; your home from the password database) and writes a fresh `config.json` there through a new file of a random name: the folders, fixed global-install patterns (npm, Python user sites, cargo, Claude Code's versions, the npx cache, plugins, editor extensions, nvm and uv runtimes, NodeSource's `nodejs`), and the scan's limits;
4. runs `skills/osv/core/osv-scan.sh` with only `PATH`, `HOME`, `LC_ALL`, `TMPDIR` and the sandbox's proxy variables. The sandbox reaches the network only through Claude Code's proxy, so those must stay; your CA and curl settings don't. The scan's own output, which holds package names, is thrown away. The scan runs in its own process group: when the runner is stopped (TERM or HUP), or after 30 minutes, it sends the group TERM, so the scan's own trap writes an ERROR result, then KILL;
5. reads `daily.json` back as untrusted, says so first if the run left no newer result, and prints fixed lines: level, notice, counts, each source's status word, the error words the core uses with a fixed hint for some, the major coverage gaps that rose (only words from the core's own list), how many lockfiles, runtime pins, Dockerfiles and virtualenvs it found below the read depth but didn't read, and whether that walk stopped early, and a fixed next step for a malware record or a fix out.

The scan is the OSV scan core: seven files, with their hashes in `skills/osv/core/SHA256SUMS`. A test in this repo pins that list, so changing the core means vendoring it again on purpose. The installed runner doesn't check the hashes (README, "The OSV check runs only when you ask"). It lists what's held, asks OSV's `querybatch` by name and version and by name at any version (for malware), asks GitHub's malware advisories by name, asks OSV's `/v1/query` (your own name and version only) for severity words and fixed versions, and checks Node.js and CPython versions against `nodejs.org` and python.org's release lists. Each reply is saved unread and reduced by `jq` to ids, dates, counts and fixed words; no reply's text, URL or name is printed or stored. Each runtime has two sources: its release list (`rt_node` from `nodejs.org`, `rt_python` from `www.python.org`) and its end-of-life data (`rt_node_eol` from `raw.githubusercontent.com`, `rt_python_eol` from `peps.python.org`). Node's end-of-life dates live on `raw.githubusercontent.com`, which setup doesn't add, so the runner's config sets `runtimes.node_schedule` false: the scan never asks that host, `rt_node_eol` says `skipped`, which never raises the level, and each Node held counts as `eol_not_checked`, never as "not past end of life". Node's security releases are checked for exact versions (nvm installs, an exact `.nvmrc` or image tag); a line-only pin such as `.nvmrc` 20 or `FROM node:20` isn't checked at all here. The runner prints up to three fixed lines, counted from each runtime row's fixed words: Node versions whose end of life isn't checked (expected; line pins included), Node line pins not checked at all, and CPython versions whose end of life a failed fetch left unchecked (not expected). A source that couldn't be read once after a good run is INFO in the core, not an ERROR, so the hook says nothing about it; the runner prints its hint with that note, and a second failure in a row is an ERROR.

`hooks/osv_status.py` runs when a session starts or resumes. It does nothing unless your user settings hold setup's OSV write entry. Then it makes the results folder (mode 700) if it's missing, since the sandboxed scan can write the folder but not make its parents, and prints nothing when the result is fresh and holds nothing to act on. Otherwise it gives you one fixed line each for a malware record (however old), a failed or unfinished check, held high or critical issues with a fix out (at any level), and a check that's due (over 24 hours) or stale (over 36). It also says when there's no result yet, or when the result can't be read or trusted. It trusts `daily.json` only when it's a plain file you own that others can't write. If it runs out of time before it has printed, it gives the "can't be read" line, not nothing. Claude gets fixed codes (`osv_alert`, `osv_error`, `osv_severe_with_fix`, `osv_due`, `osv_stale` and the like), fixed instructions and the same fixed lines: pass the lines on once, at the end of its first reply in the conversation (not again for the same lines, and not into output in a fixed format), never read the result files even if asked, and not run or change the check unless the user has just typed `/stranger-danger:osv`. The desktop app didn't show a hook's `systemMessage` when checked once (another plugin's hook, not this plugin's), so there Claude's reply may be the only way the line reaches you, if the app runs this hook and Claude passes it on (VERIFY row O3). The update reminder doesn't do this, since a note telling an agent to suggest something reads like what the rules teach it to refuse; the OSV line is different because a malware record is urgent, and what Claude passes on is the fixed line, digits only, not a suggestion of its own.

Setup's OSV option merges `templates/osv.json`: the five hosts into `sandbox.network.allowedDomains`, and the results folder into `sandbox.filesystem.allowWrite`. The folder sits under `~/.cache`, outside every path setup write-denies, so adding it leaves those denies in place. The settings guard accepts setup's plan with or without it. Setup refuses the option when the results folder would sit inside a folder setup write-denies (a Claude config folder under `~/.cache`). The doctor's `osv check`, `osv tools` and `osv result` lines say whether it's set up (setup's exact write entry, the hook's own test), whether a write deny of yours covers the folder, whether its tools are there, and how old the last result is; its `osv coverage` lines say how many lockfiles, runtime pins, Dockerfiles and virtualenvs below the read depth weren't read, and whether the walk below it stopped early.

## Failure

These are the gates' rules; the update reminder, the canary fill, the prompt scan, the instruction-file check, the OSV status hook and the terminal gate's after-hook never block. Bad JSON, a missing tool input or Bash command, a config problem or any exception exits 2, which blocks. (An event with no tool name, or a reader-tools event with no agent, is a main-session call or not a tool call, and passes.) Each gate sets `onFailure: "block"`, so on Claude Code 2.1.295 and later a hook that runs past its 15-second timeout blocks the call. Each script also sets an internal alarm (3 s for the launch gate, 5 s for the reader gate, the reader-tools hook and the settings guard, 6 s with an 8 s backstop for the terminal gate) that exits 2 before that timeout. 2.1.295 is the minimum supported version; older ones let a timed-out call through. The `|| exit 2` in the hook command blocks if Python itself fails to start.

## Log

Every deny a hook decides, and each failed DNS lookup in the reader gate, is appended as one JSON line to `~/.local/state/stranger-danger/decisions.jsonl` (created with mode 0600; the log file itself isn't followed if it's a link, and a file that isn't a regular file, or has a second name (a hard link), isn't written to). A timeout, or a hook that fails before its code runs, blocks without a line. A call two hooks refuse, such as a reader's Bash, is logged once by each. A line holds:
- the time;
- the decision and the reason code. Launch-gate codes start with `launch-` and name the kind of refusal, such as `launch-launcher` or `launch-privilege`; the reader-tools hook's start with `reader-tools`;
- the tool;
- the claimed `agent_type`;
- for the reader gate only, the path (escaped) or the URL's host.

It never holds file contents, command text, query strings or search terms. If the log can't be written, the decision doesn't change. Each hook writes it before its alarm is cleared, so a write that stalls in a way a signal can interrupt still ends in a block. The shared writer takes only the codes and decisions the hooks use (`_log.KNOWN_CODES`); anything else is written as `invalid-code` or `invalid`, so an event's input can't reach those fields by mistake.

The log stays on your machine; nothing sends it anywhere. It stops growing at 20 MB, so a hijacked agent that triggers refusals in a loop can't fill the disk; the write that would cross that adds a `log-full` line instead, padded to reach the cap, and the coordinator's page and the report flag a log that has reached the cap, judged by its size. The log isn't tamper-proof: the Edit and Write tools are denied there and sandboxed commands can't write there, but a command that runs outside the sandbox can.
